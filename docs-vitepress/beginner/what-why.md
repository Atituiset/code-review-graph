# 这个项目是什么、解决什么问题

## 一句话介绍

code-review-graph 是一个本地优先（local-first，指数据和计算都留在你自己的机器上）的代码知识图谱工具。它预先把整个代码仓库解析成一张"符号关系图"——函数、类是图里的节点，调用、继承、导入、测试这些关系是节点之间的边——存进本地的一个 SQLite 数据库。当 AI 编码助手（如 Claude Code、Cursor）要做代码审查时，它不再把整个仓库塞进上下文，而是从图里精确取出与本次改动相关的那一小片，连同风险评分一起交给 AI。

如果说 README 是项目的名片，这篇文档想回答的是名片背后的三个问题：它到底在解决什么痛点？为什么"预先建图"是对的解法？接入之后我的日常流程会变成什么样？读完你应该能判断这个项目值不值得装进自己的工具箱。

本篇不涉及任何命令操作，安装和第一次使用留给下一篇《快速上手》。阅读时不用记任何细节，抓住一个主线即可：**仓库的信息总量不变，变的是"每次喂给 AI 多少、喂哪部分"**——code-review-graph 的全部设计都围绕这个取舍展开。

## 它要解决什么问题

### 问题一：把仓库整个塞进上下文，既不现实也烧钱

AI 编码助手本质上是一个大语言模型（LLM，Large Language Model），它每次"思考"能看到的文字量是有限的，这个量用 **token**（可以粗略理解为"词元"，一个英文单词或一个汉字大约折合一两个 token）来计量，称为上下文窗口。把仓库里所有文件都发给 AI，有三个直接后果：

- 中大型仓库根本装不下，超出上下文上限；
- 就算装得下，API 按 token 计费，每次审查都全量发送会非常烧钱；
- 塞进来的 99% 代码和本次改动无关，反而稀释了 AI 的注意力，审查质量下降。

### 问题二：grep / 全文检索给不了"结构"

不用全量发送，那就按需搜索？`grep` 这类工具确实能找到"某个函数名出现在哪些文件里"，但它不理解代码的结构：

- 它分不清一处 `connect` 是函数**定义**、**调用**还是注释里随手提到的单词；
- 它不知道"改了这个函数，会有哪些调用者被波及"，需要人工一条条点进去追；
- 它不知道哪些函数有测试覆盖、哪些是安全敏感代码（比如密码、鉴权相关的函数）。

也就是说，全文检索只有"文本"，没有"关系"。而代码审查恰恰最需要关系：这次改动动了谁？谁会受影响？有没有测试兜住？

### code-review-graph 的思路：先建图，再切片

code-review-graph 把成本从"每次审查时"挪到了"事前"：

1. **建图**：用 tree-sitter（一个高性能的多语言语法解析器，能把源码解析成结构化的语法树）把仓库里每个文件解析一遍，抽出所有函数、类、类型、测试，以及它们之间的调用、继承、导入、测试关系，形成一张图。
2. **本地存储**：这张图存在仓库目录下的 `<repo>/.code-review-graph/graph.db` 里，就是一个普通的 SQLite 数据库文件（见 `code_review_graph/incremental.py:367`）。SQLite 是嵌入式数据库，不需要装任何服务端，一个文件就是整个数据库。
3. **审查时取切片**：当你改了代码，工具根据 git diff 定位到改动涉及的函数节点，沿着图中的边向外走几步（调用者、被影响的执行路径、相关测试），只把这一小片上下文，加上每个改动函数的风险评分，打包交给 AI。

打个比方：全文检索像在一座城市里沿街喊名字找人；code-review-graph 则像先画好了一张标着道路和门牌的地图，之后每次只需要在地图上圈出目的地周围两个街区。

## 和现有手段的关系

code-review-graph 不是要替代你已有的工具，而是补上一层它们给不了的东西：

| 手段 | 擅长 | 给不了什么 |
| --- | --- | --- |
| `grep` / 全文搜索 | 快速找文本出现位置 | 分不清定义、调用和注释；不知道谁受影响 |
| IDE 的"跳转到定义/查找引用" | 人机交互式的单点跳转 | 结果是给人逐条看的，没法批量打包给 AI |
| 让 AI 自己读文件 | 灵活、无需准备 | 读多少靠猜，大仓库里又慢又贵还容易漏 |
| code-review-graph | 结构化关系 + 按预算切片 | 运行时才确定的关系（静态分析的天花板） |

实际工作里它们会共存：AI 先用图定位到"值得读的那几个函数"，再用普通文件读取细看——图负责"找对地方"，精读负责"看懂细节"。

## 它怎么接入你的工作流

code-review-graph 提供两个入口：

- **MCP server**：MCP（Model Context Protocol，模型上下文协议）是 AI 工具与外部服务通信的一套开放协议——可以把它理解为"AI 工具界的 USB 接口"：只要两边都支持 MCP，AI 工具就能发现对方提供哪些工具（tool）、传入参数、拿到结构化结果，而不需要为每个服务单独写适配层。code-review-graph 把自己封装成一个 MCP server，Claude Code、Cursor、Windsurf 等支持 MCP 的 AI 工具可以直接调用它提供的工具（查图、算影响面、取审查上下文等）。运行 `code-review-graph install` 可以自动检测你装了哪些 AI 工具并写好对应的 MCP 配置（见 `code_review_graph/cli.py:613`）。
- **独立 CLI**：命令行程序 `code-review-graph`，提供 `build`、`update`、`detect-changes`、`query` 等子命令，适合脚本、CI（持续集成，指每次提交代码后自动跑测试/检查的流水线）流水线，或者不接 MCP 的平台。

一条重要的边界：**纯本地运行，代码不出本机**。解析、建图、查询全部发生在你的机器上。唯一可能联网的环节是语义搜索用的向量 embedding（把代码片段转成向量以便按"意思相近"搜索）：默认的 `local` provider 也是本地模型，只有当你显式把 provider 配置成 `openai` / `google` / `minimax` / `voyage` 这类云端服务时，代码摘要才会发到外部（见 `code_review_graph/cli.py:817` 的 `embed` 命令）。

## 为什么叫"知识图谱"

"知识图谱"（knowledge graph）这个词来自搜索引擎行业：谷歌把"人名—作品—公司"这类实体和关系织成网，让搜索从"匹配关键词"升级为"理解实体之间的关系"。code-review-graph 借用的是同一个思想，只是实体换成了代码符号：

- **实体**：函数、类、文件、类型、测试；
- **关系**：调用、继承、实现、导入、包含、测试覆盖。

一旦关系被结构化地存下来，"这次改动影响谁""这个函数的测试在哪""仓库大致分几个模块"这类问题就变成了图查询，毫秒级返回，而且结果稳定可复现——这是让 AI 现场 grep 多少次都换不来的。图构建是一次性投入，之后每次审查、每个问题都从同一张图上切片。

## 一次审查实际发生什么

用一个具体例子把流程串起来。假设你在 `auth.py` 里改了 `login` 函数，然后让 AI 审查这次改动：

1. AI 调用 `detect_changes_tool`，工具用 git diff 找到 `auth.py` 变了，进而在图里定位到节点 `auth.py::UserService.login`；
2. 沿着 `CALLS` 边反向找到它的调用者，沿 `TESTED_BY` 边查它有没有测试，沿流表查它出现在哪些执行流里，综合算出一个 0 到 1 的风险评分；
3. AI 再调用 `get_review_context_tool`，工具把这些相关节点的源码片段按 token 预算裁剪打包——改动的函数全文保留，外围调用者只给签名或关键行；
4. AI 拿到的不是几千个文件，而是一份带优先级排序的"审查简报"：改了谁、风险多少、波及哪些流、哪些改动没有测试。

整个过程里，全仓库的信息都在图上，但真正进入 AI 上下文的只有这一小片。这就是"建图一次，切片每次"的含义。

## 支持哪些语言

解析基于 tree-sitter，内置覆盖了主流语言：Python、JavaScript/TypeScript（含 JSX/TSX）、Go、Rust、Java、C#、Ruby、C/C++、Kotlin、Swift、PHP、Scala、Dart、Lua、Elixir、Julia、Zig、Solidity、Vue、Svelte、Bash、PowerShell 等（扩展名到语言的映射表见 `code_review_graph/parser.py:713-767`）。没有现成语法包的语言（如 ReScript）会用基于正则的提取兜底。

## "按 token 预算裁剪"具体怎么裁

这是让 AI 用得起的最后一公里。工具返回结果时有几个档位和上限在起作用（以 `get_review_context_tool` 为例，见 `code_review_graph/main.py:289-312`）：

- **`detail_level`**：`standard` 返回完整结果，`minimal` 只返回压缩摘要——初筛用 minimal，锁定目标后再要 standard；
- **`max_depth`**：影响半径默认只向外走 2 层，不会无限扩散；
- **`max_lines_per_file`**：每个文件最多截取指定行数（默认 200），改动的核心函数给全文，外围代码只给关键片段；
- **`max_results`**：查询类工具默认最多返回 100 条，防止一个热门函数的调用者清单把上下文撑爆。

这些默认值的经验法则是：宁可少给、让 AI 追问，也不要一次倾倒。图的存在让"追问"变得很便宜——再查一次只是几毫秒的图查询，而不是重新扫描仓库。

## 边界与取舍

诚实地说清楚它不适合什么，和说清楚它适合什么同样重要：

- **图需要保持新鲜**。图谱是预构建的，代码变了图不会自动变——需要 `update` 增量更新、`watch` 监听，或装 hooks 自动触发。作为兜底，每个 MCP 工具的返回都会附带一段 provenance（来源信息）：图的构建时间、建图时的 git 提交、以及"当前 HEAD 是否与建图时一致"的标志（`code_review_graph/tools/_common.py:60-120`），AI 可以据此发现图已过期并提醒你更新。
- **静态分析有天花板**。tree-sitter 做的是静态解析（只看代码文本，不运行程序），所以运行期才确定的关系——比如反射、动态导入、依赖注入容器在运行时才绑定的实现——可能解析不出来或只能部分解析。对这类代码，图给的是"尽量好的近似"，不是完整真相。
- **第一次建图有成本**。全量 `build` 要解析整个仓库，大仓库需要等一会儿；之后增量更新通常很快。
- **`detect-changes` 是只读的**。它只分析已有图谱，不会重新解析文件（`code_review_graph/cli.py:982`）；图过期时先用 `update`。
- **评分是启发式，不是裁决**。风险评分、criticality 这些数字来自一组人工设定的权重（比如"没测试 +0.30"），作用是排序和提醒，而不是证明"这段代码一定有 bug"。把它们当审查的优先级建议，结合人脑判断使用。

## 关键事实速览

- 项目形态：Python 包 `code_review_graph/`，当前版本 2.3.7（`pyproject.toml:7`），需要 Python 3.10 及以上。
- 命令行入口：`code-review-graph`（主 CLI）和 `crg-daemon`（多仓库监听守护进程），见 `pyproject.toml:48-50`。
- 图的存放位置：`<repo>/.code-review-graph/graph.db`，一个普通的 SQLite 文件。
- 交付给 AI 的内容：与改动相关的代码切片、风险评分、测试缺口、受影响的执行流，并按 token 预算裁剪——给多少上下文由预算决定，而不是由仓库大小决定。
- 隐私边界：解析、存储、查询全在本机；云端 embedding（把代码转向量用于语义搜索）必须显式选择 `openai`/`google` 等 provider 才会启用，默认 `local` 也是本地模型。

## 常见问题

**需要联网吗？** 不需要。建图、更新、查询、MCP 服务全部在本地完成。唯一的例外是你显式选择云端 embedding provider 时，语义搜索的向量计算会调用对应厂商 API；默认的 `local` provider 用本地模型，同样不联网。

**支持哪些 AI 工具？** `install` 命令可以自动检测并配置：Claude Code、Codex、Cursor、Windsurf、Zed、Continue、OpenCode、Antigravity、Gemini CLI、Qwen、Qoder、Kiro、GitHub Copilot（含 CLI）、CodeBuddy 等（完整清单见 `code_review_graph/cli.py:55-59`）。不在清单里的工具，只要能跑命令，也可以直接用 CLI 方式集成。

**代码会被上传到别处吗？** 不会。图数据库 `<repo>/.code-review-graph/graph.db` 就在你的仓库目录里，你可以直接删除它，也可以用 `code-review-graph uninstall` 彻底清理。建图时它还会被自动加入 `.gitignore`，不会误提交。

**和我正在用的 AI 助手冲突吗？** 不冲突。code-review-graph 不改你的代码、不改 AI 工具本身，只是注册为一个 MCP server，给 AI 多提供一批可调用的工具。AI 觉得图有用就调用，觉得直接读文件更合适就直接读。

**支持 monorepo（多包大仓库）吗？** 支持。`register` / `repos` 子命令维护一个多仓库注册表，`crg-daemon` 可以同时监听多个仓库，MCP 侧也有跨仓库搜索能力（`code_review_graph/cli.py:931-944`、`code_review_graph/main.py:948`）。这部分属于进阶用法，本篇不展开。

## 本篇术语表

把本篇出现的术语集中放在这里备查：

- **token**：大语言模型计量的最小文本单位，上下文长度和 API 费用都按它计算；
- **LLM（Large Language Model）**：大语言模型，AI 编码助手的核心；
- **上下文窗口**：模型单次能看到的 token 总量，装不下的部分模型完全不知道；
- **tree-sitter**：多语言语法解析器，把源码文本解析成结构化的语法树，是建图的基础；
- **SQLite**：嵌入式数据库，整个数据库就是一个文件，无需安装服务端；
- **MCP（Model Context Protocol）**：模型上下文协议，AI 工具与外部服务互通的开放标准；
- **git diff**：两次提交（或工作区与某提交）之间的文件差异，change 检测的输入；
- **embedding（向量嵌入）**：把文本转成一串数字向量，使"意思相近"可以按距离计算；
- **hook（钩子）**：编辑器/AI 工具在特定事件（如保存文件、调用工具前）自动触发的脚本；
- **daemon（守护进程）**：在后台长期运行的程序，这里指多仓库文件监听进程；
- **CI（Continuous Integration）**：持续集成，提交代码后自动构建、测试的流程。
