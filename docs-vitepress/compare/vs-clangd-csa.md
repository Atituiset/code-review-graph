# 与 clangd / CSA 的本质区别

把 code-review-graph 和 clangd、Clang Static Analyzer（CSA）放在一起比较，初看是"静态分析工具之间的横向对比"，实际上三者几乎不在同一个平面上竞争：clangd 是面向人类编辑器的语言服务器，CSA 是依附于编译流程的符号执行引擎，而 code-review-graph 是面向 LLM agent 的代码知识图谱。它们的差异不是"谁做得更好"，而是"设计前提根本不同"。本章从五个维度展开：分析对象与前提、语义深度、输出与消费方、性能与规模、互补关系。

## 总览表

| 维度 | clangd | CSA | code-review-graph |
|------|--------|-----|-------------------|
| 分析前提 | 需要 `compile_commands.json`，完整预处理与类型检查 | 依附 Clang 编译流程，拦截编译动作 | 零配置，tree-sitter 直接解析源文件 |
| 语言覆盖 | C/C++ 为主（含少量相关语言） | C/C++/Objective-C | 约 40 种内建语言 + `languages.toml` 扩展 |
| 语义深度 | 真实类型系统、重载决议、宏展开、跨翻译单元索引 | 路径敏感符号执行（exploded graph）、约束求解 | 无类型系统、无数据流、无路径敏感，启发式建边 |
| 输出消费方 | 人类编辑器（跳转/补全/重构） | 人类审查者（bug 报告） | LLM agent（JSON 切片 + token 预算） |
| 精度要求 | 极高（错误跳转直接损害信任） | 高（但允许一定误报换检出率） | 中等（启发式精度换覆盖面和速度） |
| 延迟要求 | 毫秒级（交互式） | 分钟到小时级（CI/nightly） | 秒级构建 + 毫秒级查询 |
| 典型失效模式 | 编译数据库缺失/过期时全面退化 | 路径爆炸，大函数超时放弃 | 命名唯一性假设失效时静默给出错误边 |

## 一、分析对象与前提

### clangd：编译正确性是入场券

clangd 建立在 Clang 前端之上，它分析的从来不是"源文件文本"，而是"某个具体编译配置下的翻译单元"。这带来一个硬性前提：必须有编译数据库（`compile_commands.json` 或 `compile_flags.txt`），告诉它每个文件的 include 路径、宏定义、语言标准、目标三元组。没有这个数据库，clangd 会退化为"猜"——头文件找不到、宏没展开、模板无法实例化，跳转和补全大面积失灵。

这个前提在工程上是合理的：C/C++ 的语义本身就依赖预处理结果，`#ifdef` 分支、`-D` 宏、include 搜索顺序都会改变代码的含义。clangd 选择"先正确、后分析"，把编译配置当作不可省略的输入。

### CSA：寄生在编译流程上

CSA 更进一步：它不是一个独立运行的分析器，而是 Clang 编译管线上的一段旁路。`scan-build` 这类工具的工作原理是拦截编译动作，在生成 AST 之后驱动符号执行引擎。因此 CSA 继承了 clangd 的全部前提——代码必须能被 Clang 前端完整处理，分析才能开始。

### code-review-graph：放弃编译前提，换取零配置

code-review-graph 走了相反的路。它用 tree-sitter 直接解析源文件文本，不需要编译数据库、不需要 include 路径、不需要宏展开，甚至代码编译不过也能解析——tree-sitter 的容错解析（error recovery）会在语法错误处生成 ERROR 节点并继续，而不是整体失败。语法层面的健壮性由 grammar 子进程探活等机制兜底（见 `code_review_graph/parser.py:506` 的探活失败记录、`:5521` 的 `_MAX_AST_DEPTH` 防御）。

代价是明显的：它看到的是"代码的结构"，而不是"代码在某个编译配置下的语义"。换来的是约 40 种内建语言开箱即用，加上 `languages.toml` 的用户级扩展，对一个混用语言栈的仓库（Python + TypeScript + Terraform + YAML）可以一条命令建图，不需要为每种语言准备构建环境。

**这是最根本的分野**：clangd/CSA 把"可编译"当作分析的入场券，code-review-graph 把"可解析"当作唯一前提。前者买到语义深度，后者买到覆盖面和零配置。

## 二、语义深度

### clangd：真实类型系统与跨翻译单元索引

clangd 拥有 Clang 的完整语义分析能力：重载决议、模板实例化、隐式转换、宏展开后的真实 token 流。它的跨翻译单元索引（基于 index 分片的后台索引）能回答"这个虚函数的所有覆写""这个符号在项目里的所有引用"这类问题，且结果在类型层面是精确的——它知道两个同名函数里哪个是 `void f(int)`、哪个是 `void f(double)`，知道一次调用经过 ADL 实际绑定到哪个声明。

这种精度直接支撑了重命名重构这类"改错一处就编译失败"的操作：IDE 敢让用户一键重命名，前提是引用列表在类型层面完备。这也是 clangd 与任何语法级工具之间最宽的鸿沟。

### CSA：路径敏感的符号执行

CSA 的核心引擎是路径敏感的符号执行：它把函数体展开成 exploded graph（程序点 × 符号状态的乘积空间），沿每条可行路径维护符号值的约束，用约束求解器（当前默认基于 Z3 的求解）裁剪不可行路径。checker 挂在图遍历的回调上，因此能发现真正意义上的深层 bug：

- 空指针解引用（某条路径上指针未判空）；
- use-after-free、双重释放、内存泄漏（追踪堆区域的生命周期状态机）；
- 除零、数组越界、未初始化值使用；
- 锁顺序、整数溢出（部分 checker 默认关闭）等。

这类发现是语法级工具在原理上无法做到的，因为它们依赖"沿某条具体路径，某个值的状态是什么"这一路径敏感事实。

### code-review-graph：命名唯一性启发式

code-review-graph 明确放弃了所有这些深度：无类型系统、无数据流分析、无动态派发解析、无路径敏感。它的跨文件调用解析是一个两阶段启发式：

1. **解析期留证据**：单文件解析时把 receiver、限定名等信息存进边的 `extra` JSON；
2. **构建后修补**：resolver 在图构建完成后批量扫描未决引用，在候选节点中匹配——几乎所有 resolver 都遵循"候选唯一才收编，多候选放弃或降级"的保守策略（见进阶篇《语义解析层：Resolver 机制》）。

这个策略的基石是**命名唯一性假设**：如果整个仓库里只有一个叫 `process_order` 的函数，那么对 `process_order(...)` 的未决调用大概率指向它。在中小型代码库里这个假设大体成立；在大型多模块代码库里（几十个 `Handler.handle`、几十个 `__init__`）它系统性失效——而且是**静默失效**：多候选时 resolver 放弃建边，图上表现为"没有调用关系"，没有任何警告告诉你这里丢了一条边。

诚实地说，这是设计取舍而非缺陷：引入真正的类型推断意味着引入 clangd 式的编译前提，零配置和 40+ 语言覆盖会立刻瓦解。code-review-graph 至少做了两件缓解措施：

- 推断产生的边统一标记 `confidence_tier='INFERRED'`，与直接抽取的 `'EXTRACTED'` 区分（`code_review_graph/graph.py:103`），下游消费方可以按置信度过滤；
- resolver 全部设计为"可失败"——单个 resolver 抛异常不会中断构建，只是少了它负责的那部分边。

但这终究是启发式的天花板：它能告诉你"这里**可能**有一次调用"，永远无法告诉你"这里**确实**调用了 `Derived::f` 而不是 `Base::f`"。

### 一个具体的对照示例

用同一个 C++ 虚函数调用说明三者的差距最直观：

```cpp
void dispatch(Processor& p) { p.handle(req); }
```

- clangd 知道 `p` 的静态类型是 `Processor&`，能列出 `handle` 的所有覆写并精确定位每一处引用——因为它做了完整的类型检查和类层次分析；
- CSA 不关心"调了谁"，它关心沿每条路径 `p` 是否可能为空、`req` 是否已释放——这是状态机与约束求解的问题；
- code-review-graph 看到的是一次 receiver 为 `p` 的 `handle` 调用，resolver 在候选节点里找 `handle`：全仓库唯一就收编并标 `INFERRED`，有多个 `handle` 就放弃——它不知道静态类型，更不会尝试动态派发解析。

三种答案没有对错之分，只有"回答的是不是你要问的问题"之分。

## 三、输出与消费方

### clangd：服务人类编辑器

clangd 的输出是 LSP 响应：跳转位置、补全列表、hover 类型、重命名编辑。消费方是一个盯着屏幕、反应时间以百毫秒计的人。这决定了它的两个硬指标：**高精度**（跳错一次定义，用户信任就崩了）和**低延迟**（补全超过一两百毫秒就会被感知为卡）。

### CSA：服务人类审查者

CSA 的输出是 bug 报告（HTML/plist），消费方是愿意花时间甄别误报的审查者。这允许它慢（nightly 跑几小时可以接受），也允许它有一定误报率——只要检出率足够高、报告可审计（带路径事件的 exploded path），人可以做最终裁决。

### code-review-graph：服务 LLM agent

code-review-graph 的消费方不是人，是 LLM agent。这改变了一切输出设计：

- **结构化 JSON 切片**而非人类可读报告——agent 需要机器可解析的节点/边/摘要；
- **token 预算裁剪**——上下文窗口是最稀缺资源，工具按预算返回片段；
- **预计算摘要表**——`community_summaries`、`flow_snapshots`、`risk_index` 把社区结构、执行流、风险热点物化到 SQLite，查询时不用临时遍历全图；
- **极俭入口**——官方提示词要求 agent 先调 `get_minimal_context`（约 100 token 的项目概览），所有工具默认 `detail_level="minimal"`，只在需要时升级到 `standard`/`verbose`（`code_review_graph/prompts.py:20-23`）。

精度要求也因此不同。人类编辑器用户被错误跳转坑一次就会弃用；LLM agent 对"图上少了一条边、多了一条低置信边"有天然的容错——它本来就在处理不确定性，只要大体结构正确、置信度有标注，启发式误差是可以接受的。code-review-graph 正是用精度换了 agent 真正需要的东西：**跨语言的覆盖面、零配置的可用性、token 经济的输出**。

## 四、性能与规模

### clangd：慢构建、快增量

clangd 的索引构建是重量级操作：每个翻译单元都要完整走完预处理 + 语义分析，大型 C++ 项目的全量索引以十分钟到小时计。但增量路径经过极致优化——preamble 机制把文件头部的 include 部分预编译缓存，编辑函数体时只需重译 preamble 之后的部分，交互延迟压到毫秒级。

### CSA：路径爆炸

CSA 是三者中最慢的。exploded graph 的规模随分支数指数增长，引擎靠预算（最大节点数、最大步数、超时）强行截断，大函数上"预算耗尽、放弃分析"是常态而不是例外。它的合理定位就是 CI/nightly 级别的深度检查，永远不可能塞进交互式工作流。

### code-review-graph：快构建、简单增量，但有截断

code-review-graph 的构建很快：tree-sitter 解析是线性语法分析，没有类型检查、没有符号执行，中型仓库全量构建通常在秒到分钟级。增量更新靠一个朴素但可靠的模型：git diff 确定变更基点、watchdog 监听工作区变动、SHA-256 hash 短路未实际变化的文件。

需要注意两个已知的规模边界：

1. **依赖追溯截断**：`find_dependents` 反向追溯依赖时默认只展开 2 跳、最多收编 500 个文件（`code_review_graph/incremental.py:944-945`），超限后截断并打上 `truncated` 标记。大改动波及面超过这个范围时，增量更新的影响分析是不完整的——设计上有标记，但消费方不检查标记就会漏。
2. **C++ 变更全量重建**：C/C++ 相关解析逻辑的变更（grammar 升级、identity 规则调整）会直接触发全量重建，成本转嫁到用户的下一次构建。

### 一句话比较

clangd 是"重资产投入换交互体验"，CSA 是"无上限算力换 bug 检出率"，code-review-graph 是"轻量语法分析换随时可用的全貌"。三者的性能画像与它们的消费方完全自洽。

值得注意的是三者对"增量"的理解完全不同：clangd 的增量是文件内粒度的（preamble 复用），目标是把一次按键的代价压到最低；CSA 基本没有有意义的增量，每次分析近似从头再来；code-review-graph 的增量是文件间粒度的（哪些文件变了、波及哪些依赖），目标是把一次提交的代价压到最低。粒度差异再次印证了消费方差异：编辑器按击键收费，CI 按提交收费，agent 按审查任务收费。

## 五、互补关系

结论是：三者不构成替代关系，在一个严肃的 C++ 项目里它们各管一段。

- **clangd 管编辑精度**：开发者写代码时的跳转、补全、重构，需要真实类型系统背书，这是 code-review-graph 原理上给不了的；
- **CSA 管深层 bug**：空指针、泄漏、use-after-free 这类路径敏感缺陷，只有符号执行能挖，知识图谱连数据流都没有；
- **code-review-graph 管 AI 审查上下文与跨语言架构视图**：LLM agent 审查一个 PR 时需要的是"改了哪些函数、影响哪些流、风险热点在哪、相关测试是什么"，并且这些答案要在几百到几千 token 内给出；面对混合语言仓库时还需要一张统一的架构图——这正是 clangd/CSA 都不提供的东西。

实践中两者甚至可以同时使用：AI agent 完全可以在同一个会话里既挂 code-review-graph 的 MCP（拿图谱切片和架构概览），又挂 clangd 的 MCP（在 C++ 文件里做精确的符号查询与重构）。前者负责"看全局、省 token"，后者负责"抠细节、保正确"，各取所长。

选择的标准从来不是"哪个工具更强"，而是"当前任务的消费方是谁、对语义深度的真实需求是多少"。

## 附：三个常见误解

最后澄清三个在讨论中反复出现的误解：

1. **"code-review-graph 是穷人版 clangd"**——不是。clangd 解决的是编辑精度问题，code-review-graph 解决的是 agent 上下文供给问题，两者的核心交付物（LSP 响应 vs token 预算切片）根本不重叠。
2. **"加上类型推断就能追上 clangd"**——加不了。真正的类型推断需要预处理、include 解析和编译配置，一旦引入就等于重做 Clang 前端，零配置和多语言覆盖会同时瓦解。未接线的 `jedi_resolver.py` 恰恰说明：即使在类型系统相对友好的 Python 上，真类型推断也还停留在实验阶段。
3. **"CSA 能发现深层 bug，所以图谱的风险评分没价值"**——两者测的不是一种东西。CSA 找的是路径敏感的确凿缺陷，code-review-graph 的风险评分是给 agent 排审查优先级的启发式信号；前者是判定，后者是导航。
