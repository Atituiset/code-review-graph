# 优点、不足与适用场景

本章对 code-review-graph 做一次不吹不黑的盘点：它解决了什么真问题、在哪些地方存在原理性或工程性的天花板、什么样的团队和工作流适合用它，什么样的任务应该交给别的工具。结论先行：**它是一个非常称职的"LLM agent 代码上下文供应商"，但不是一个通用静态分析平台**——把它用在设计边界之内，体验很好；越界使用，会撞上启发式精度的墙。

## 优点

这些优点不是并列罗列，它们其实服务于同一个目标：让 AI agent 在任何代码库上都能以最低摩擦获得结构化上下文。理解这条主线，就能理解各项设计决策的由来。

### 零配置的多语言支持

约 40 种语言内建开箱即用，不需要编译数据库、不需要构建环境、不需要为每种语言准备工具链。tree-sitter 的容错解析保证代码编译不过也能建图。`languages.toml` 还允许用户自行扩展新语言。对混合语言仓库（后端 Python + 前端 TypeScript + 基础设施 Terraform）来说，"一条命令建全仓库的图"是实打实的价值——这是 clangd 类工具在原理上给不了的体验，因为它依赖真实编译配置，而混合仓库恰恰很难为所有语言都备齐编译环境。

### 框架感知，不只是语法感知

内置了一批框架级 resolver，能理解语法之外的语义惯例：Spring 的依赖注入（`spring_resolver.py`）、Temporal 的 workflow/activity wiring（`temporal_resolver.py`）、Terraform/HCL 的资源引用（`hcl_resolver.py`）、TypeScript 的路径别名（`tsconfig_resolver.py`）等。这些边是纯语法分析拿不到的，对"看懂一个真实项目"帮助很大——真实代码库里的调用关系有相当比例藏在框架约定里，而不是显式的函数调用里。

### 本地优先，隐私友好

全部数据在本地 SQLite 里，代码不出机器。对不能上云的企业代码库，这是合规层面的硬优势，也天然避免了把私有代码喂给第三方索引服务的风险。顺带的好处是没有外部服务依赖：离线环境、内网环境、CI 沙箱里都能工作。

### 体系化的 token 经济设计

这不是"顺便支持一下 LLM"，而是从存储到查询的系统性设计：预计算摘要表（`community_summaries`、`flow_snapshots`、`risk_index`）把常用聚合物化入库；`get_minimal_context` 用约 100 token 给出项目概览；所有工具默认 `detail_level="minimal"` 并按 token 预算裁剪输出（提示词层面的约定见 `code_review_graph/prompts.py:20-23`）。在上下文窗口即成本的时代，这套设计直接换算成钱和延迟。

### 工程防御性强

代码库里随处可见"假设一切都会失败"的设计：

- grammar 加载放到子进程里探活，加载崩了不会拖死主进程（`code_review_graph/parser.py:506`）；
- 所有 resolver 都可失败——单个 resolver 抛异常只是少建一部分边，构建照常完成；
- AST 深度有硬性上限（`_MAX_AST_DEPTH = 180`，`code_review_graph/parser.py:5521`）；
- schema 迁移幂等，重复执行不出错；
- 边的置信度分层：`confidence_tier` 区分 `EXTRACTED`（语法直接抽取）与 `INFERRED`（启发式推断），下游可按需过滤（`code_review_graph/graph.py:103`）。

### 简单可靠的增量模型

git diff 确定变更基点 + watchdog 监听 + SHA-256 hash 短路未变文件，配合 SQLite WAL 的并发读写模型，整套增量机制没有花哨成分，胜在行为可预测、失败模式可理解。hash 短路尤其值得点名：mtime 变化但内容未变的文件不会触发重解析，watch 大量文件时的无效工作量被压到很低。

## 不足

先说明盘点的口径：以下不足都来自对源码的直接核实，而不是推测。有些条目（如未接线的模块、暴力扫描）在 README 和宣传材料里看不到，只有读代码才能发现——这也是本章存在的意义。

### 跨文件解析的精度天花板

这是最本质的一条。跨文件调用解析建立在**命名唯一性假设**上：未决引用只在候选唯一时被收编，多候选则放弃或降级。在大型多模块代码库里，同名函数俯拾皆是（几十个 `handle`、几十个 `run`），这个假设系统性失效——而且是**静默失效**：边没有被建出来，图上表现为"没有调用关系"，没有任何信号告诉你这里丢了一条边。审查者看到的可能是一张缺边的图而不自知。这是用启发式换零配置的固有代价，短期内无法根治。

### parser.py 的可维护性

`code_review_graph/parser.py` 单文件 16080 行，40 种语言的解析逻辑全部塞在一个文件里，是典型的"上帝文件"。新增语言、修 bug、code review 都要在这个庞然大物里翻找，长期维护成本和合并冲突风险都在累积。拆分成本本身不高（按语言拆模块即可），但文件越大，拆分的回归风险越让人望而却步——这是典型的会自我恶化的债。

### 启发式缺乏数据验证

风险评分、社区划分、影响半径的权重本质上都是人工调出来的启发式，缺乏在标注数据集上的系统性验证。"风险分数 0.8"意味着什么、误报率多少，目前没有数据支撑。仓库里有 eval/ 目录和 benchmark 工具的雏形，但尚未形成可信的精度报告。

使用建议上，这意味着应把这些分数当作"排序信号"而非"绝对度量"：比较 A 函数比 B 函数风险更高是有意义的，断言"0.8 等于 80% 概率出 bug"是没有依据的。

### 半成品未接线

- `code_review_graph/jedi_resolver.py`（303 行）：基于 Jedi 的真类型推断 resolver，理论上能大幅改善 Python 跨文件解析精度，但存在而未接入构建管线；
- `code_review_graph/memory.py`（142 行）：记忆功能，同样未接线。

这些死代码/半成品意味着部分宣传中的能力是"路修了一半"，用户实际拿到的功能比代码体积暗示的要少。评估项目成熟度时，应该以"接线进构建管线的功能"为准，而不是以仓库里存在的文件为准。

### 向量搜索是暴力扫描

语义搜索的向量相似度是 Python 层的暴力余弦 O(N) 全表扫描，没有 ANN 索引（如 HNSW）。节点数上到几万之后，每次语义搜索的延迟会线性劣化；这对"语义搜索"这个卖点功能是一个实打实的规模上限。

### test_gaps 的误报倾向

测试覆盖缺口分析只认直接的 `TESTED_BY` 边（`code_review_graph/graph.py:614`）。通过继承 fixture 间接覆盖的代码、参数化测试、以及"测试调了被测函数的调用方"这类间接覆盖，都容易被误判为"无测试覆盖"，在重度使用 fixture 的代码库里误报会偏多。

### C++ 变更的成本转嫁

C/C++ 相关解析逻辑（grammar、identity 规则）一旦变更，直接触发全量重建——这是把维护者的正确性成本转嫁给用户的构建时间。大型 C++ 仓库的用户会在升级后付出一次全量构建的代价。

这个设计的合理性在于：identity 规则变化后旧图的节点标识不再可信，增量修补反而更危险。但"合理"不改变成本的存在，升级前应有心理预期。

### 其他已知边界

- `find_dependents` 反向追溯默认 2 跳、500 文件截断（`code_review_graph/incremental.py:944-945`），大改动的增量分析可能不完整；
- daemon 没有 IPC，健康检查只有活/死二元状态，无法查询构建进度或排队任务。

### 不足的结构性归因

把上面这些不足摆在一起看，会发现它们分成三类，应对方式也不同：

- **原理性天花板**：命名唯一性启发式、无类型/无数据流——这是放弃编译前提的直接推论，只能通过接线 jedi 这类真实推断局部缓解，无法整体消除；
- **工程债**：parser.py 上帝文件、向量 O(N) 扫描、daemon 无 IPC——有明确的修法，是时间和优先级问题；
- **验证缺口**：风险评分、test_gaps 的启发式缺乏数据集背书——需要的是 benchmark 建设和精度报告，而不是改算法。

区分这三类很重要：对原理性天花板应该调低预期，对工程债可以等版本迭代，对验证缺口则应该在采信具体分数时自行抽查。

## 适用场景

先给判断标准：**当一个任务的核心需求是"以可控的 token 成本，让 AI 快速理解一个可能混用语言、可能没有构建环境的代码库的全局结构"时，code-review-graph 是目前少数认真回答了这个问题的工具**。具体展开：

- **AI 辅助代码审查（主打场景）**：`detect_changes` + 影响半径 + 流分析 + 风险摘要，按 token 预算喂给 LLM agent，这是整个工具链设计的主线，完成度最高；
- **多语言/多仓库架构概览**：社区划分 + `community_summaries` 能让 agent 或新人快速建立"这个仓库由哪几块组成、块与块怎么连"的心智模型，跨语言统一视图是差异化能力；
- **token 敏感的 agent 工作流**：预算即成本，预计算摘要 + minimal detail level 的设计在这里回报最大；
- **无编译环境的遗留代码库**：拿不到构建脚本、编译不过的老代码，clangd/CSA 全部失效，tree-sitter 容错解析是少数还能工作的方案。

这四类场景有一个共同特征：它们要的都是"结构性的理解"而非"语义上的判定"。凡是落在这个特征里的任务，code-review-graph 的性价比都很高；一旦任务的本质是"判定对错"（这个引用是不是那个定义、这条路径上有没有泄漏），就越出了它的能力圈。

## 不适用场景

这三类的共同点是：它们要求的精度等级超出了启发式图谱的原理上限，而且各自都有成熟的专门工具。

- **需要精确类型信息的重构**：重命名、提取接口、签名变更这类操作要求类型层面精确的所有引用，请用 clangd（C/C++）或对应语言的 IDE/LSP——命名唯一性启发式给出的引用列表既不完整也不保证正确；
- **深层 bug 挖掘**：空指针解引用、内存泄漏、use-after-free、并发缺陷这类路径敏感问题，需要符号执行或更重的分析，请用 CSA、Coverity、CodeQL；code-review-graph 连数据流分析都没有；
- **单语言深度语义查询**："这个虚函数的所有覆写""这个接口的所有实现"在单一语言内的精确版本，成熟的语言服务器回答得更好；code-review-graph 的价值在跨语言的全局视图，不在单语言的深度。

## 使用建议：规避已知不足

了解不足之后，可以用一些低成本的习惯把风险压到最小。这些建议的共同原则是：把图谱的输出当作"需要验证的线索"，而不是"已经验证的事实"。

1. **消费 INFERRED 边时保留怀疑**：跨文件调用关系如果标着 `confidence_tier='INFERRED'`，在关键结论落地前用 Grep/LSP 抽查一两条，尤其是在大型多模块仓库里。
2. **把 test_gaps 当线索不当判决**：它报告"无测试覆盖"时，先确认是否存在继承 fixture 或参数化测试的间接覆盖，再决定是否补测试。
3. **升级版本后留意全量重建**：C++ 相关解析逻辑变更会触发全量重建，大仓库升级前预留一次构建时间窗口。
4. **语义搜索控制节点规模**：向量搜索是 O(N) 暴力扫描，节点数很大的仓库里优先用结构化查询（callers_of / tests_for 等）而非语义搜索。
5. **关键路径用专用工具兜底**：图的定位是"导航"而非"判定"，涉及重构正确性、安全缺陷的结论，交给 clangd、CSA、CodeQL 做最终确认。

## 与其他方案的组合

实际团队里最常见的组合模式：

- **AI agent + code-review-graph MCP**：agent 用图谱拿架构概览、改动影响面、风险热点，这是基础配置；
- **AI agent + code-review-graph + clangd MCP**：C/C++ 项目里，图谱管全局与 token 经济，clangd 管符号级精度，两者通过 MCP 并存互不干扰；
- **CI 里 CSA/CodeQL 做守门，图谱做审查辅助**：深层 bug 由重量级分析在 nightly 把关，日常 PR 审查的上下文供给交给图谱。

| 你要做什么 | 用什么 |
|-----------|--------|
| 让 AI agent 审查 PR / 改动 | code-review-graph |
| 给 AI agent 提供仓库架构全局视图 | code-review-graph |
| 无构建环境的遗留代码梳理 | code-review-graph |
| C/C++ 精确跳转、重构 | clangd |
| 挖空指针、泄漏等深层 bug | CSA / Coverity / CodeQL |
| 单语言深度语义查询 | 对应语言的 LSP / IDE |
| 安全漏洞与污点分析 | CodeQL / Semgrep |
| 编译期强制约束（空安全、所有权） | 编译器本身 + lint |

## 总评

如果用一句话概括 code-review-graph 的定位：**它是 LLM 时代重新回答"怎么把代码库喂给 AI"这个问题的产物**，而不是传统静态分析工具链上的又一环。它最大的优点（零配置、跨语言、token 经济）和最大的不足（启发式精度天花板）来自同一个根因——放弃编译前提。理解这个根因，就能预判它在任何具体场景下的表现：

- 任务需要的是"广度、速度、结构"，它会超出预期；
- 任务需要的是"深度、精度、判定"，它会安静地撞墙，而且撞墙时不一定发出声音——静默失效是它最需要使用者警惕的特性。

对它的公正评价是：设计目标清晰、工程实现扎实、自我认知诚实（INFERRED 标注、resolver 可失败、truncated 标记都是证据），但部分能力仍在半成品状态，启发式的精度缺乏数据背书。用在边界之内，值得推荐；把它当成静态分析的通用解法，会失望。
