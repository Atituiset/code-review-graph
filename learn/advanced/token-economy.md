# Token 经济：为 LLM 设计的上下文预算

前面六章讲"图怎么建、怎么查、怎么信"。本章讲贯穿所有章节的隐藏主线：**这个项目的真正客户不是人，是上下文窗口有限的 LLM**。对 AI 编码助手而言，上下文窗口是最稀缺的资源——塞进窗口的每个 token 都在和系统提示、对话历史、工具结果、待编辑代码抢预算；多余 token 不只是贵，还会稀释注意力、推高延迟。code-review-graph 几乎每层设计都是这个约束的推论：**把"找相关代码"这个 O(仓库) 的问题，离线压缩成查询期 O(答案) 的问题**。

## 预计算摘要：查询不展开子图

第 2 章提到的 v6 三张摘要表（`community_summaries` / `flow_snapshots` / `risk_index`，migrations.py:163-203）是 token 经济的存储侧根基。

没有它们，"给我看架构概览"意味着运行时展开社区子图、聚合统计、再裁掉九成内容——做完才发现只要 20 行摘要。有了物化摘要，常用问题的答案是**构建期付过一次钱、查询期按主键直接取**：响应体从"子图"缩成"摘要行"。把计算从读时挪到写时，是全书最反复出现的招式。

## 分层 detail_level 与 ~100 token 入口

工具输出普遍支持 `detail_level`，`minimal` 档只保留名字、规模、分数等标量字段：

- `compact_response`（tools/_common.py:320）把 `minimal` 设为默认值——详细是 opt-in，简洁是默认；
- 社区工具的 `_minimal_overview`（community_tools.py:214）把概览压缩到名字/规模/凝聚度。

最激进的是 `get_minimal_context`（`tools/context.py:49`）：docstring 直接写明目标——**约 100 token**，给 agent 一份"开工所需的最小上下文"（仓库骨架、关键入口、图统计），让它先拿骨架再按需钻取。它还带三道就绪门：图缺失、图空、图落后于 HEAD 时返回 `not_ready` 状态并指路 build 工具——最小上下文如果来自过期图，省下的 token 会连本带利变成错误结论。这是"渐进式披露"（progressive disclosure）原则在工具设计上的落地：每一层钻取都由 agent 主动发起，每一层的返回都被预算约束。

## 审查上下文的裁剪管线

`get_review_context` 类工具把"这次变更"翻译成上下文时有三道闸：

1. **行级裁剪**：`max_lines_per_file = 200`（`tools/review.py:103` 的参数默认值）。文件超限时只抽变更节点的行区间、前后各约 2 行上下文，重叠区间合并，区间之间以 `...` 分隔；且全部片段共享一个 **800 行总闸**（`_MAX_REVIEW_SOURCE_LINES`）——v2.3.8 之前只有"每文件 200 行"没有总数，N 个文件就能 N×200 行地漏过。LLM 看到的是"变更函数 + 紧邻上下文"，而不是整个文件；
2. **节点级截断**：变更函数超 500 直接截断（`CRG_MAX_CHANGED_FUNCS`，changes.py:465 读取），并在输出中明示可用环境变量调整——宁可明确截断，不静默溢出；
3. **影响半径有界**：第 5 章的 0.05 分数地板 + 500 节点上限，同时是正确性阀和 token 阀。

三道闸的共同风格：**截断永远显式**。输出里带着"被截断了、怎么调大"的信息，agent 可以自行决定要不要更多——预算的控制权留在调用方。

## 成本计量：4 字符 ≈ 1 token

`context_savings.py` 回答"图帮我省了多少"。估算用保守的 **4 字符/token** 近似（`CHARS_PER_TOKEN = 4`，context_savings.py:13），对全文上界的估算同样保守（直接拿 `st_size` 换算）。

已知偏差：4:1 是英文代码语料的经验值，**CJK 文本偏差很大**（中文在多数 BPE 分词器下每字 1~2 token，4 字符 ≈ 1 token 会严重低估）。所以提供 `verify_with_tiktoken`（context_savings.py:151）做可选校准——装了 `tiktoken` 就用真实编码器逐文件计数，与近似值对账。计量本身也奉行分层：便宜的近似默认开，精确的测量按需做。

选择"保守近似 + 可选校准"而不是默认依赖 tiktoken，还有一个部署理由：tiktoken 是原生扩展依赖，而 context_savings 可能跑在 CI、hook 等轻量环境里——近似算法零依赖、永远可用，且方向性的结论（省了一个数量级）对估算误差不敏感。

## 把 token 纪律推到 agent 侧

图工具只能保证"自己返回得少"；更大的浪费在 agent 的传统动作上——全文 Grep、整文件 Read。项目用三个机制把纪律推过工具边界：

### enrich.py：PreToolUse 拦截

作为 Claude Code 的 **PreToolUse hook**，拦截 `Grep`/`Glob`/`Bash`/`Read` 调用（enrich.py:35-38、287）：能用图结果替代全文检索时，注入替代建议或补充上下文——在 agent 即将犯下"读整个目录"这类动作**之前**拦一道。这是把预算执法从"工具内部"前移到"agent 的决策路径上"。

### hints.py：会话内 intent 推断

根据最近工具调用的特征推断意图，在每次工具结果后追加一条"下一步建议"（hints.py:15-56）：看过流 → 建议钻取单条流的逐步细节；看过架构 → 建议高层概览；改过代码 → 建议查受影响流。目标是**把 agent 引向低 token 的图查询，而不是高 token 的盲搜**——用提示塑造检索策略，而不是等盲搜发生后再裁剪。

### skills.py：写进文档的预算

生成给 agent 看的技能文档，把预算写成明文纪律：**"≤5 次工具调用完成 review/debug/refactor 任务，总输出 ≤800 token"**（skills.py:900 附近四处重复出现）。文档即策略：让 LLM 在规划阶段就知道约束，比事后裁剪有效得多。

## 为什么这套设计对 LLM 场景重要

静态分析工具的传统用户是 IDE 里的人：人会扫视、跳读、忽略噪声，结果多给 10 倍只是滚动条长一点。LLM 完全不同：

- **上下文是硬预算**。50 万行仓库的全文约 5 亿 token，任何"先把代码读进来再说"的策略在物理上不可行。检索和裁剪不是优化，是唯一能活下来的架构；
- **注意力会稀释**。塞入无关代码不只浪费额度，还实证地降低模型对关键片段的利用率——裁剪是质量手段，不只是成本手段；
- **工具调用是串行的**。每次工具往返都是秒级延迟加一轮推理，"≤5 次调用"的纪律直接决定交互可用性；
- **可复现性需求**。agent 的决策依赖工具输出，物化摘要 + 固定种子（第 5 章 Leiden seed 42）保证同一问题两次问得到同一答案，推理链可回放、可调试。

回头看，前面各章的"奇怪"选择——离线预计算一切、查询期禁止 O(图) 工作、裸边延迟解析、所有输出分层 detail_level、截断永远显式——都收敛到同一个目标函数：**单位 token 的信息密度**。这是 code-review-graph 与一般代码索引工具的分水岭：它优化的不是查询延迟，而是"让 LLM 在预算内看到恰好够用的那一小块"。

## 附：一次节省的演算

以一次典型的"审查最近一个 commit"为例，对比两条路径的 token 成本：

**传统路径（无图）**：agent 先 `git diff --stat` 看动了 12 个文件，然后逐文件 Read 全文。设平均每文件 400 行 × 约 40 字符/行 ≈ 16 KB，12 个文件 ≈ 192 KB ≈ **4.8 万 token**（4:1 估算）。这还没算理解依赖关系时追加的 Grep/Read。

**图路径**：`detect_changes` 返回变更节点 + 风险分 + 影响半径（有界 500 节点、实际通常几十个），`get_review_context` 按 200 行/文件上限裁剪、且只抽变更节点 ±2 行。典型输出 **2~4 千 token**。`context_savings.py` 就是把这两者的差值定期算给用户看的模块。

量级结论：图把单次审查的上下文成本压到传统路径的 **1/10 到 1/20**，且变更越大、仓库越大，比值越有利——传统路径随仓库规模线性恶化，图路径的成本只随**变更规模**增长。

## 附：hook 拦截的时序

enrich.py 在 Claude Code 工具调用链中的位置：

```
agent 决定调用 Grep("retry logic")
        │
        ▼
PreToolUse hook: enrich.py 从 stdin 读 hook JSON
        │
        ├─ 模式能用图回答 → 注入 semantic_search 结果/建议
        │
        └─ 不能 → 放行原调用
        ▼
agent 收到（可能被丰富的）结果，继续推理
        │
        ▼
hints.py 在结果后追加下一步建议
```

两个机制一前一后：enrich 管"这次调用别浪费"，hints 管"下次调用更聪明"。两者都通过标准 hook 协议（stdin/stdout JSON）工作，不修改 agent 本体，也不假设特定模型。

## 附：MCP 工具表面的硬预算

预算纪律最终体现在 MCP 工具的返回形状上——同一个图，喂给人的 CLI 可以啰嗦，喂给 LLM 的 MCP 工具必须克制。

这一层曾经只是"约定"：工具靠参数自律、靠摘要表省事。#849 戳破了它——`get_affected_flows` 在一个真实工作流里返回了 **约 24.7 万 token**，而那份工作流的文档写着"5 次工具调用，总计 800 token"。随后对全部 30 个注册工具在真实 5.6k 节点图上的普查又发现了十处同形态问题，最严重的默认路径上就有：`list_communities` 默认 20.6 万 token，`get_architecture_overview` 标准档 62.5 万。

v2.3.8 的回应是把约定升级成**机制**：

- 每个列表型响应过 `_bounded`（tools/_common.py:294）：硬上限截断，但 `total` 字段永远报告**未截断**的真实总数；
- 摘要行统一渲染 "showing N of M"——调用方一眼分清"答案就这么短"和"被裁了"；
- 上限参数拒绝 `<1` 和布尔值（Python 里 `True == 1` 的经典陷阱）；
- 测试侧有 `ABSOLUTE_MAX_TOKENS = 50_000` 兜底断言，且有一条回归守卫：**新注册的工具若没有预算表条目，CI 直接失败**（test_token_budget.py）。

### 预算怎么定：先测每行的钱

上限不是拍脑袋。实测了每种输出的单价（tools/review.py 头部的常量注释）：普通节点约 60 token、带风险分的节点约 118、一条完整流（含 steps）**约 980**、只有元数据的流约 18。单价差 50 倍的地方就是预算要下手的地方——于是有了**共享预算池**的设计：`get_affected_flows` 的标准档给全部返回流一个共 400 step 的总池，最关键的流先花，尾部流保留元数据、标 `steps_omitted: true`；`detect_changes` 干脆只嵌元数据版流。

### 诚实清单：还没封顶的四个

普查也如实留下了四个最坏情形未封顶的工具（issue #888 追踪）：`get_impact_radius` 的 changed_nodes/edges 不受 max_results 约束、`find_large_functions` 与 `semantic_search_nodes` 的 limit 未设上限、`traverse_graph` 的 token_budget 未设上限。它们的**默认参数**预算仍被测试断言着——失控需要调用方主动传大值，但边界没有收口。第 6 章的"诚实清单"在这里同样适用：写文档的人有义务告诉你哪里还疼。

## 附：provenance——每个响应都带图的身份证

token 经济解决"返回多大"，还有一个配套问题："这个答案基于多新的图？"几乎每个 MCP 工具的响应都被 `with_provenance` 包上一层 `_graph` 元数据（tools/_common.py:60）：构建时间、图龄（秒）、构建时的 commit 与分支、以及 `head_matches_build` ——用只读模式（`mode=ro`）打开 SQLite 读出 build SHA，与实时 `git rev-parse HEAD` 对比。注意措辞的精确性：它只声明 commit 是否一致，**不**声明工作区是否干净——这是 #458 讨论后的刻意收敛，一个布尔字段只说一句真话。agent 看到 `age_seconds: 3600` 就知道该先 update 再信结果；这与第 6 章 uncertainty 的陈旧检测共享同一套元数据底座。




## 附：常见误用

- **把 `detail_level` 开到 full 当默认**：详细档是给"已定位到具体目标、确实需要全貌"准备的；拿它做探索等于绕过分层设计，预算立刻失控；
- **绕过图工具直接让 agent 全文 Grep**：enrich.py 能拦一部分，但根本解法是技能文档（skills.py 产物）被 agent 真正读到——部署时确认技能文档进了 agent 的系统提示；
- **用 4:1 估算值对外汇报 CJK 仓库的节省**：会系统性高估节省比例（估算的分母偏小），需要对外数字时跑 `verify_with_tiktoken` 校准；
- **把截断当 bug**：`truncated: true`、"use CRG_MAX_CHANGED_FUNCS to adjust" 这类标记是设计的一部分，正确反应是按需调大或缩小审查范围，而不是期待无界输出；
- **在每次工具调用后人工追加背景**：hints.py 已经在做下一步建议，重复的人工背景注入只会占预算——信任分层机制，必要时调它的参数而不是绕开它。

## 小结

token 经济不是这个项目的一个功能模块，而是它的架构公理：存储层（v6 摘要表）、查询层（有界松弛、分层 detail_level）、输出层（行级裁剪、显式截断）、agent 交互层（hook、hints、技能文档）四个层次各自独立地执行同一条纪律。理解这一点之后，读代码时遇到的几乎每个"为什么不直接……"的疑问，答案都是同一个：因为那会把 O（仓库） 的成本放回查询路径上，而查询路径上的每个 token 都是 LLM 从自己的思考预算里支付的。

至此，token 经济作为架构公理的叙述完成。下一章把视角转向唯一常驻运行的部分——watch 模式的可靠性工程；对比篇则将把整套设计与 clangd/CSA 等传统静态分析方案对照，进一步澄清它做了什么取舍、适合什么场景。

## 附：二阶效应
token 经济还有几个不那么直观的推论，值得在评估或二次开发时记住：

- **与 local-first 互相成就**：离线预计算之所以可行，是因为图就在本机 SQLite 里，预计算不花 API 钱；反过来预计算又让在线查询小到可以塞进任何模型的窗口。两个设计目标互为前提；
- **成本确定性**：所有上限都是硬常数（500 节点、200 行、500 函数），一次工具调用的 token 成本有可计算的上界——这对需要预算审计的团队场景（CI 里跑 AI 审查）比"平均很快"重要；
- **引导 agent 的检索策略本身就是功能**：hints/skills 的文档不是辅助材料，而是系统行为的一部分——删掉它们，同样的工具表面会退化成"agent 照旧全文 Grep"。评估这个项目时要把这部分"软实力"计入；
- **反向约束**：一旦接受"返回必须小而稳"，工具表面就不能提供"导出整个子图"这类 API——功能取舍是被预算纪律反向塑造的。想给项目加功能的贡献者需要先回答"它的 token 上界是多少"。
